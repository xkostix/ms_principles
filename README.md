### Задание 1

Задача 1: API Gateway

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:

    маршрутизация запросов к нужному сервису на основе конфигурации,
    возможность проверки аутентификационной информации в запросах,
    обеспечение терминации HTTPS.

Обоснуйте свой выбор.

### Решение

Если к трем требованиям добавить требование "Крупная компания", а также декларативное управление через GitOps/CI/CD, то получаем следующие параметры сравнения и выбор.

Берем распространенные api-gateway: Kong Gateway, KrakenD, Traefik, Apache APISIX.

KrakenD не поддерживает «горячую» перезагрузку конфигурации (hot reload) без перезапуска процесса. Исключаем его.

NGINX Plus в контексте крупной компании и подходов GitOps/CI/CD концептуально уступает специализированным API Gateway (Kong, APISIX), оставаясь в первую очередь классическим балансировщиком нагрузки и обратным прокси. И он является платным коммерческим продуктом. В NGINX Plus проверка JWT-токенов (модуль auth_jwt) является платной enterprise-фишкой, но она довольно базовая. Для более сложной логики в NGINX Plus придется либо писать громоздкие интеграции на JavaScript / Lua, либо докупать сторонние модули. В Kong и APISIX это решается включением одного готового и гибко настраиваемого YAML-плагина. Плюс высокая стоимость лицензирования при масштабировании. Поэтому NGINX Plus я исключаю.


| Критерий / Возможность | **Kong Gateway** | **Apache APISIX** | **Traefik** |
| :--- | :--- | :--- | :--- |
| **Масштаб и Enterprise-фишки** | **Эталон на рынке.** Огромное сообщество, коммерческая поддержка, проверен во множестве крупных компаний. | **Высокий.** Популярен в крупных тех-компаниях (Tencent, Baidu), активно развивается под эгидой Apache. | **Средний/Высокий.** Отличное решение, но в сложных enterprise-топологиях уступает Kong/APISIX по гибкости плагинов. |
| **GitOps / Декларативное управление (YAML)** | **Идеально (DB-less режим + decK).** Утилита `decK` позволяет полностью валидировать, синхронизировать и откатывать конфигурацию из YAML. Нативно работает как K8s Ingress Controller через CRD. | **Отлично (Режим Standalone).** Поддерживает чтение `apisix.yaml` без etcd. Также имеет мощный `apisix-ingress-controller` для Kubernetes на базе декларативных ресурсов. | **Идеально (Родная фишка).** Вся конфигурация изначально декларативная (YAML/TOML). В Kubernetes динамически управляется через Custom Resource Definitions (CRD) или Ingress. |
| **Маршрутизация по конфигурации** | Полная поддержка (NGINX-based). | Полная поддержка (Сверхбыстрый движок Radix Tree). | Полная поддержка (Динамическое сопоставление правил). |
| **Проверка аутентификации** | Десятки готовых плагинов (OIDC, JWT, Key-auth, OAuth2). | Десятки готовых плагинов + легкое расширение на Go/Java/Python/Wasm. | Встроенные Middleware (JWT через сторонние плагины или Forward Auth). |
| **Терминация HTTPS** | Да (Высокая производительность NGINX). | Да (Динамический TLS без перезагрузок). | Да (Автоматический Let's Encrypt + кастомные сертификаты). |

### Выбор решения: **Kong Gateway**. Готовность к Enterprise-масштабам и GitOps и соответствие прочим критериям.

Однако, возможно, стоит выбрать **Apache APISIX** в случае если: крупная компания делает ставку на ультра-низкий latency (микросекунды) и инженеры хотят писать кастомные плагины на Java или Python (в Kong основной язык — Lua), то Apache APISIX в Standalone-режиме (чтение из YAML) станет главным и единственным конкурентом Kong, который также полностью закроет задачи компании.
