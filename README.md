### Задание 1

Задача 1: API Gateway

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:

    маршрутизация запросов к нужному сервису на основе конфигурации,
    возможность проверки аутентификационной информации в запросах,
    обеспечение терминации HTTPS.

Обоснуйте свой выбор.

### Решение

Если к трем требованиям добавить требование "Крупная компания", а также декларативное управление через GitOps/CI/CD, то получаем следующие параметры сравнения и выбор.

Берем распространенные api-gateway: Kong Gateway, KrakenD, Traefik, Apache APISIX.

KrakenD не поддерживает «горячую» перезагрузку конфигурации (hot reload) без перезапуска процесса. Исключаем его.

NGINX Plus в контексте крупной компании и подходов GitOps/CI/CD концептуально уступает специализированным API Gateway (Kong, APISIX), оставаясь в первую очередь классическим балансировщиком нагрузки и обратным прокси. И он является платным коммерческим продуктом. В NGINX Plus проверка JWT-токенов (модуль auth_jwt) является платной enterprise-фичей, но она довольно базовая. Для более сложной логики в NGINX Plus придется либо писать громоздкие интеграции на JavaScript / Lua, либо докупать сторонние модули. В Kong и APISIX это решается включением одного готового и гибко настраиваемого YAML-плагина. Плюс высокая стоимость лицензирования при масштабировании. Поэтому NGINX Plus я исключаю.


| Критерий / Возможность | **Kong Gateway** | **Apache APISIX** | **Traefik** |
| :--- | :--- | :--- | :--- |
| **Масштаб и Enterprise-фишки** | **Эталон на рынке.** Огромное сообщество, коммерческая поддержка, проверен во множестве крупных компаний. | **Высокий.** Популярен в крупных тех-компаниях (Tencent, Baidu), активно развивается под эгидой Apache. | **Средний/Высокий.** Отличное решение, но в сложных enterprise-топологиях уступает Kong/APISIX по гибкости плагинов. |
| **GitOps / Декларативное управление (YAML)** | **Идеально (DB-less режим + decK).** Утилита `decK` позволяет полностью валидировать, синхронизировать и откатывать конфигурацию из YAML. Нативно работает как K8s Ingress Controller через CRD. | **Отлично (Режим Standalone).** Поддерживает чтение `apisix.yaml` без etcd. Также имеет мощный `apisix-ingress-controller` для Kubernetes на базе декларативных ресурсов. | **Идеально (Родная среда).** Вся конфигурация изначально декларативная (YAML/TOML). В Kubernetes динамически управляется через Custom Resource Definitions (CRD) или Ingress. |
| **Маршрутизация по конфигурации** | Полная поддержка (NGINX-based). | Полная поддержка (Сверхбыстрый движок Radix Tree). Standalone: присутствует задержка на периодический опрос конфига. В обычном режиме применение мгновенно. | Полная поддержка (Динамическое сопоставление правил). |
| **Проверка аутентификации** | Десятки готовых плагинов (OIDC, JWT, Key-auth, OAuth2). | Десятки готовых плагинов + легкое расширение на Go/Java/Python/Wasm. | Встроенные Middleware (JWT через сторонние плагины или Forward Auth). |
| **Терминация HTTPS** | Да (Высокая производительность NGINX). | Да (Динамический TLS без перезагрузок). | Да (Автоматический Let's Encrypt + кастомные сертификаты). |


2 решения выходят в финал: Kong Gateway и Apache APISIX. **APISIX Standalone** идеологически и архитектурно наиболее близок к **Kong Gateway в режиме DB-less**, поскольку оба решения полностью отказываются от централизованных баз данных в пользу декларативных файлов конфигурации (YAML).
Решение зависит от того:
* Как часто меняются или добавляются новые маршруты
* Какой объем конфигурации ожидается (десятки, сотни или тысячи микросервисов и эндпоинтов)

Поэтому сравнение по маршрутизации требует дополнительного сравнения:


| Критерий | Apache APISIX (Traditional) | Apache APISIX (Standalone) | Kong Gateway (Traditional) | Kong Gateway (DB-less) |
| :--- | :--- | :--- | :--- | :--- |
| **Источник правды (Runtime)** | Кластер `etcd` | Локальный YAML-файл (`apisix.yaml`) | Реляционная БД (`PostgreSQL`) | Локальный YAML-файл (`kong.yml`) |
| **Как доставляется GitOps-код** | Git -> GitOps-оператор -> Admin API -> `etcd`. | **Git -> GitOps-оператор (ArgoCD/Flux) -> Kubernetes ConfigMap / файл на диске**. | Git -> GitOps-оператор -> Admin API -> `PostgreSQL`. | **Git -> GitOps-оператор -> Инструмент deck (CLI) / Admin API**. |
| **Задержка применения (Git -> Шлюз)** | Минимальная (<1 сек после отработки оператора). | **Зависит от синхронизации ConfigMap в K8s (обычно 10–30 сек)**. | Средняя (зависит от оператора + интервала опроса БД нодами). | Средняя (зависит от времени выполнения утилиты `deck sync`). |
| **Поведение шлюза при обновлении** | Атомарное обновление Radix Tree в памяти без деградации трафика. | **Инкрементальное обновление Radix Tree в памяти напрямую из файла без перезагрузки процессов Nginx**. | Локальный сброс кэша нод, возможен кратковременный рост Latency на «холодные» запросы. | Полная перезапись конфигурации в памяти. На гигантских YAML-файлах возможен всплеск CPU. |
| **Инфраструктурный оверхед** | Высокий (нужно разворачивать и администрировать отказоустойчивый `etcd`). | **Минимальный (база данных не нужна, шлюз полностью автономен)**. | Высокий (нужно администрировать, бэкапить и масштабировать `PostgreSQL`). | Минимальный (база данных не нужна, но требуется утилита `deck` для валидации и пуша). |


Выбор решения: **Kong Gateway**. Готовность к Enterprise-масштабам и GitOps и соответствие прочим критериям.

Однако, возможно, стоит выбрать **Apache APISIX** в случае если: крупная компания делает ставку на ультра-низкий latency (микросекунды) и инженеры хотят писать кастомные плагины на Java или Python (в Kong основной язык — Lua), то Apache APISIX в Standalone-режиме (чтение из YAML) станет главным и единственным конкурентом Kong, который также полностью закроет задачи компании. Для Kubernetes-среды (через APISIX Ingress Controller) Standalone-режим будет идеален, но не для ВМ-инфораструктуры. Другой вариант: Apache APISIX без Standalone (с etcd): становится полноценным и мощным конкурентом Kong. Его производительность и гибкость написания плагинов на любых языках (Java, Python, Wasm) превосходят Kong. Если у команды есть опыт администрирования etcd (или проект живет в Kubernetes), этот вариант будет идеальным и полностью закроет все требования, включая GitOps через утилиту adc.

Traefik остался в сравнении как главный эталон простоты и автоматизации. Но у него слабая встроенная аутентификация: У Traefik нет такого богатого выбора плагинов аутентификации. Он хорош как Ingress-контроллер (входная точка в кластер), но у него нет богатых возможностей как у других.

### Задание 2. Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:

    поддержка кластеризации для обеспечения надёжности,
    хранение сообщений на диске в процессе доставки,
    высокая скорость работы,
    поддержка различных форматов сообщений,
    разделение прав доступа к различным потокам сообщений,
    простота эксплуатации.

Обоснуйте свой выбор.

### Решение

Для сравнения берем три главных индустриальных лидера: Apache Kafka (эталон для логов и стриминга), RabbitMQ (классический брокер очередей) и Apache Pulsar (современная cloud-native платформа).


| Критерий / Требование | **Apache Kafka** | **RabbitMQ** | **Apache Pulsar** |
| :--- | :--- | :--- | :--- |
| **Кластеризация и надежность** | **Отлично.** Нативная репликация партиций. Современный встроенный механизм **KRaft** убирает зависимость от ZooKeeper, обеспечивая высокую надежность. | **Хорошо.** Поддерживает кластеризацию и кворумные очереди (Quorum Queues), но при сетевых разделениях (split-brain) требует строгой настройки. | **Идеально.** Архитектура разделена на Data Plane (BookKeeper) и Stateless Compute (Brokers), что делает масштабирование и отказоустойчивость эталонными. |
| **Хранение на диске** | **Постоянное (Log-centric).** Все сообщения пишутся на диск в append-only лог. Чтение не удаляет данные, что позволяет перечитывать их. | **Временное (Queue-centric).** Данные сбрасываются на диск для надежности, но **удаляются сразу** после подтверждения доставки (ACK). | **Постоянное (Сегментное).** Данные надежно сохраняются распределенным слоем Apache BookKeeper на дисках. |
| **Скорость работы** | **Сверхвысокая пропускная способность** (миллионы msg/sec) за счет последовательного I/O и Zero-copy, но инсталляция имеет чуть более высокий инкрементальный latency. | **Низкая задержка (Low Latency)** на небольших объемах. При переполнении очередей и сбросе на диск скорость резко падает. | **Высокая пропускная способность** и гарантированно низкий latency даже при больших объемах накопившихся сообщений. |
| **Различные форматы** | **Полная поддержка.** Брокер работает с сообщениями как с набором байт. Схемы (JSON, Avro, Protobuf) управляются через Schema Registry. | **Полная поддержка.** Работает с любыми бинарными данными. Поддерживает протоколы **AMQP, MQTT, STOMP** из коробки. | **Полная поддержка.** Имеет встроенную (native) поддержку Schema Registry и мультипротокольность. |
| **Разделение прав (RBAC/ACL)** | **Отлично.** Строгий контроль доступа (ACL) на уровне топиков и групп потребителей через SASL/SSL. | **Отлично.** Гибкое разграничение прав (Vhosts, теги пользователей, права на очереди/обменники). | **Идеально.** Родная поддержка **мультитенантности** (разделение на Tenants и Namespaces) — топ-уровень для крупных корпораций. |
| **Простояние эксплуатации** | **Средняя.** Требует понимания работы партиций и потребителей. С переходом на **KRaft** администрирование стало значительно проще (минус одна сущность). | **Высокая (Самый простой).** Имеет великолепный **веб-интерфейс из коробки**. Легко разворачивается и не требует сложной инфраструктуры. | **Низкая (Очень сложный).** Требует управления тремя слоями: ZooKeeper + BookKeeper + Pulsar Brokers. Огромные накладные расходы на DevOps. |


Финальный выбор решения: Apache Kafka. Для крупной компании, учитывая баланс между жесткими техническими требованиями и фактором простоты эксплуатации, оптимальным и обоснованным выбором является Apache Kafka.


Обоснование выбора:

1. Соответствие критерию «Простота эксплуатации» (Эффект KRaft): Исторически Kafka была сложной из-за ZooKeeper. В современных версиях протокол KRaft позволяет разворачивать метаданные внутри самой Kafka. По сравнению с Apache Pulsar (которому до сих пор нужны компоненты BookKeeper и ZooKeeper), администрирование кластера Kafka силами DevOps-команды крупной компании стало значительно проще и прозрачнее.
2. Предсказуемое хранение на диске и скорость: Требование постоянного хранения данных на диске в Kafka реализовано как фундаментальная основа архитектуры (Append-only commit log). За счет этого Kafka выдает стабильно высокую скорость и не деградирует по производительности при накоплении миллионов сообщений в очередях, в отличие от RabbitMQ.
3. Безопасность Enterprise-уровня: Встроенные механизмы авторизации (ACL) позволяют четко изолировать потоки данных (топики). Разные департаменты крупной компании смогут безопасно работать в одном кластере, не имея доступа к чужим коммерческим или персональным данным.
4. Независимость от формата данных: Kafka не валидирует структуру данных внутри себя (работает как с byte array), что позволяет передавать любые форматы (JSON, Thrift, Protobuf, Avro). При этом экосистема Confluent Schema Registry позволяет централизованно контролировать эволюцию схем данных.
5. Экосистема и кадры: Для крупной компании критически важно наличие специалистов на рынке. Kafka является стандартом де-факто для высоконагруженных систем. Найти инженеров, умеющих ее готовить, мониторить и развивать, в разы проще, чем под Apache Pulsar.

Когда стоит выбрать RabbitMQ: Если в приоритете компании стоит максимально простая эксплуатация, объемы данных умеренные (до 10-20 тыс. msg/sec), и нужна сложная маршрутизация "из коробки", а не сквозное хранение логов.
